# 《無漏》Visual Harness 產品與技術 ROADMAP

版本：0.1（討論草案）  
更新日期：2026-08-01  
範圍：`visual_harness/` 圖像資產、節點畫布、批次任務與品質驗收  

## 1. 產品定位

Visual Harness 的目標不是假裝桌面生圖程式可以無人操作，而是建立一條可追蹤、可批次處理、可重現的半自動圖像製作管線：

> 小說章節與視覺聖經 → 場景任務 → 桌面版 Codex／Gemini 人工生圖關卡 → 圖片匯入 → 自動品質驗收 → 人工核准或重試

桌面生圖是正式的人工作業節點，不列為系統缺陷。系統應自動化其前後所有重複工作，並且誠實顯示任務正在等待人工處理，而不是標示為「Live Render」。

## 2. 成功定義

第一個可投入使用的版本必須讓使用者完成以下閉環：

1. 從角色資產庫選擇已核准的角色參考圖集。
2. 建立一個或多個章節場景任務。
3. 在畫布中連接角色、物品、風格、場景與桌面生圖節點。
4. 一次匯出一批可交給 Codex／Gemini 桌面版執行的任務包。
5. 將生成圖片放回收件匣後，自動對應原任務與參考資產。
6. 執行真實的技術、角色、服裝、構圖與色彩驗收。
7. 合格圖片進入核准資產庫；不合格圖片產生修正建議並進入重試佇列。
8. 關閉頁面後重新開啟，畫布、任務、圖片與驗收結果仍可完整還原。

## 3. 不做事項

首個正式版本暫不追求：

- 以非官方方式控制 Codex／Gemini 桌面程式。
- 無人監督的自動上傳、按鍵操作或帳號操作。
- 在畫布內訓練 LoRA 或大型模型。
- 多人即時協作。
- 手機上編輯大型節點圖；手機版先以檢視與核准為主。
- 用單一分數取代人工美術判斷。

## 4. 核心產品原則

### 4.1 資產優先

角色不是一段 Prompt，而是一個可版本化的資產。每張場景圖都必須能追溯使用了哪個角色版本、哪些參考圖、哪個 Prompt、哪個引擎與哪次生圖任務。

### 4.2 圖結構是唯一事實來源

畫布不能只畫出連線。節點、連線、位置、參數與狀態必須存成可讀取、可版本控制的 JSON 工作流。

### 4.3 引擎能力分離

Codex、Gemini、Midjourney、Flux／SDXL 對參考圖片數量、權重和控制方式不同。畫布使用共同資料模型，各引擎轉接器負責產生相容的任務包，不把某個引擎參數寫死在共用資料中。

### 4.4 驗收必須來自實際圖片

Prompt Token Coverage 只屬於生成前檢查。生成後的品質結論必須讀取實際圖片；無法判斷時顯示「不可評估」，不得以固定分數自動通過。

### 4.5 人工決策可追蹤

人工可以覆核自動結果，但必須留下核准者、時間、原因與採用版本，供日後調整驗收門檻。

## 5. 目標資訊架構

桌面版前端採三欄加底部工作列：

- 左欄：角色／物品／場景／風格資產庫，以及批次任務佇列。
- 中央：可拖拉、縮放、連線與保存的節點畫布。
- 右欄：所選節點的屬性、引擎參數、版本、驗收結果與歷史。
- 底部：批次匯出、等待桌面生圖、匯入進度、驗收與人工核准工作列。

建議前端基礎：Vite + React + TypeScript + `@xyflow/react`。現有 Dashboard 可保留為視覺風格參考，但不繼續在單一 HTML 檔內堆疊畫布邏輯。

## 6. 角色資產模型

每個角色至少包含：

```json
{
  "character_id": "qin_woulou",
  "reference_set_id": "qin_woulou-core-v1",
  "version": 1,
  "status": "approved",
  "identity": {
    "canonical_name": "秦無漏",
    "visual_anchors": [],
    "forbidden_traits": []
  },
  "references": [
    { "role": "face_front", "path": "...", "sha256": "..." },
    { "role": "face_three_quarter", "path": "...", "sha256": "..." },
    { "role": "profile", "path": "...", "sha256": "..." },
    { "role": "full_body", "path": "...", "sha256": "..." },
    { "role": "outfit", "path": "...", "sha256": "..." }
  ],
  "engine_bindings": {
    "gemini": { "reference_roles": [], "notes": "" },
    "midjourney": { "mode": "engine_specific", "weight": null },
    "flux": { "adapter": null, "weight": null }
  }
}
```

必要規則：

- 一個角色可有多個 Reference Set，例如日常服、戰鬥服、受傷狀態與年齡階段。
- 每個 Reference Set 必須有唯一版本、檔案雜湊與核准狀態。
- 合成三視圖可以保留，但應另外提供乾淨的臉部、側面與全身裁切圖。
- 角色、服裝、姿勢和風格是不同參考用途，畫布不得將它們混成單一無型別圖片輸入。
- 已被場景任務引用的版本不得原地覆蓋，只能建立新版本。

## 7. 節點與連線模型

首批正式節點：

| 節點 | 輸入 | 輸出 | 用途 |
|---|---|---|---|
| Character Reference Set | 無 | `CHARACTER_REF` | 選擇角色與版本 |
| Item Reference Set | 無 | `ITEM_REF` | 選擇法寶或關鍵物品 |
| Style Reference | 無 | `STYLE_REF` | 全書或章群視覺風格 |
| Scene Spec | 章節資料 | `SCENE_SPEC` | 鏡位、人物、動作、情緒與環境 |
| Prompt Composer | 各種 Reference + Scene | `PROMPT_PACKAGE` | 建立引擎中立 Prompt |
| Engine Adapter | Prompt Package | `DESKTOP_JOB` | 轉成 Codex／Gemini 等任務格式 |
| Desktop Generation Gate | Desktop Job | `CANDIDATE_IMAGE` | 表示人工桌面生圖與等待匯入 |
| Quality Gate | Candidate + References | `QA_REPORT` | 執行真實圖像驗收 |
| Human Approval | Candidate + QA Report | `APPROVED_ASSET` | 核准、退回或覆核 |

連線必須具備型別驗證。例如 `STYLE_REF` 不得接入角色臉部輸入口；同一場景可以連接多個角色 Reference Set，但每個角色必須有明確的場景角色名稱。

## 8. 任務狀態機

```text
draft
  → ready
  → exported
  → awaiting_desktop_generation
  → awaiting_import
  → imported
  → qa_running
  → needs_review
  → approved
  ↘ rejected → retry_ready → exported
```

異常狀態：

- `blocked_missing_reference`
- `blocked_invalid_workflow`
- `import_unmatched`
- `import_duplicate`
- `qa_not_assessable`
- `qa_failed`

每次狀態轉換都要保存時間、來源與原因。

## 9. 批次桌面生圖交接格式

每次匯出建立一個不可變的批次資料夾：

```text
exports/batches/<batch_id>/
├── manifest.json
├── TASKS.md
├── prompts/
│   └── <job_id>.md
└── references/
    └── <job_id>/
```

`manifest.json` 記錄任務 ID、章節、角色版本、引擎、Prompt、參考圖、期望尺寸與輸出檔名。`TASKS.md` 提供適合貼入桌面程式的批次指示。

匯入圖片命名規則：

```text
<job_id>--<candidate_id>.<png|jpg|webp>
```

收件匣只接收圖片，不透過檔名推測角色或章節；所有對應關係來自 `manifest.json`。

## 10. 真實品質驗收分層

### Level 0：檔案與技術檢查

- 圖片可解碼、格式允許、尺寸與比例符合。
- 檔案雜湊、重複圖片與缺檔檢查。
- 任務 ID、候選 ID 與批次 Manifest 可以對應。

### Level 1：視覺規範檢查

- 實際圖片色盤、亮度、對比與飽和度。
- 禁止元素與明顯風格漂移。
- 文字、水印、邊框與圖像破損。

### Level 2：角色一致性檢查

- 臉部可見時，比對角色臉部 Embedding。
- 臉部不可見時，改以服裝、髮型、體態與特徵物判斷，並降低信心值。
- 多角色場景分別產生評分，不使用整張圖單一角色分數。
- 先以人工標記樣本校準門檻，避免固定閾值造成誤判。

### Level 3：場景與敘事檢查

- 人物數量、角色身分、關鍵物品、場景與鏡位。
- 章節要求的動作、情緒與禁用內容。
- 無法由本地模型可靠判斷的項目交由人工核准，不偽造高分。

### 驗收輸出

每張候選圖產出結構化 `qa_report.json`，包含分項分數、信心值、證據、不可評估項目、失敗原因與建議修正 Prompt。Dashboard 只能讀取這份報告，不得使用寫死數字。

## 11. 分階段 ROADMAP

### Phase 0：基線與資料契約

狀態：下一步  
目標：移除目前資料路徑與展示資料不一致的問題，先確立後續不會反覆重做的契約。

交付物：

- 角色 Reference Set、工作流、任務、批次 Manifest 與 QA Report 的 JSON Schema。
- 修正不存在的 `anchor_registry` 路徑，統一資產目錄。
- 將現有秦無漏三視圖登記為 `qin_woulou-core-v1`。
- 引擎能力表，區分 Codex、Gemini、Midjourney 與 Flux／SDXL。
- 將固定測試數字標記為 demo 或移除。

完成條件：

- 所有現有角色與圖片通過 Schema 驗證。
- 任一圖片都能追溯角色、版本、來源與雜湊。
- Dashboard 不再引用不存在的檔案。

### Phase 1：可重用角色資產庫

目標：讓角色圖片真的可以跨章節與跨任務重用。

交付物：

- 角色資產列表、搜尋、狀態與版本檢視。
- Reference Set 建立、核准與建立新版本。
- 多張參考圖的用途標記與裁切預覽。
- 角色、服裝、姿勢、物品與風格資產分類。
- 引擎相容性警告與參考圖數量限制。

完成條件：

- 同一角色 Reference Set 可被至少三個場景任務引用。
- 更新角色時不會改寫既有任務使用的版本。
- 匯出的任務包包含正確的參考圖與用途說明。

### Phase 2：真實節點畫布

目標：以真正的圖資料取代固定 HTML 與 SVG。

交付物：

- React Flow 畫布與自訂節點。
- 拖拉、Pan、Zoom、Fit View、Mini Map、框選與刪除。
- 型別化 Handles、連線驗證與循環檢查。
- Save／Load、Undo／Redo、複製節點。
- 節點 Inspector 與錯誤狀態。
- 工作流 JSON 匯入、匯出與版本號。

完成條件：

- 重新整理頁面後節點、連線、位置與參數不變。
- 無效連線會被阻止並顯示原因。
- 可以從空白畫布建立一條可驗證的完整生圖工作流。

### Phase 3：批次任務與桌面交接

目標：一次準備多個場景，只把必要的人工作業留給桌面生圖程式。

交付物：

- 批次任務建立與佇列。
- Codex／Gemini 桌面任務包匯出器。
- 任務狀態機與等待人工操作畫面。
- 圖片收件匣、檔名／Manifest 對應與重複檢查。
- 缺圖、錯圖與無法對應圖片的處理介面。

完成條件：

- 可一次匯出至少二十個場景任務。
- 匯回圖片後，所有符合命名規則的圖片都能自動對應原任務。
- 系統不把等待桌面操作顯示成自動生成中。

### Phase 4：真實圖像品質驗收

目標：用實際圖片取代固定 Palette、CLIP 與 Face 分數。

交付物：

- Level 0–3 驗收執行器。
- 角色臉部／視覺特徵評估技術選型 PoC。
- 真實色盤與圖像品質檢查。
- 多角色、遠景、遮臉與無臉場景處理。
- QA Report、失敗證據與門檻設定。
- 人工標記校準資料集。

完成條件：

- 所有 Dashboard 分數都來自可追溯的 QA Report。
- 不可可靠判斷的圖片會標記為 `qa_not_assessable`。
- 至少以三十組人工標記樣本校準自動門檻並記錄誤判。

### Phase 5：核准、重試與成品庫

目標：完成從候選圖片到正式小說資產的閉環。

交付物：

- 候選圖比較、人工核准、退回與覆核。
- 依 QA 失敗原因產生修正 Prompt。
- 重試任務與版本歷史。
- 核准圖片庫、章節關聯與使用紀錄。
- 批次與角色一致性趨勢頁。

完成條件：

- 每張核准圖片都能追溯完整生成與驗收歷史。
- 退回圖片可一鍵建立保留原脈絡的重試任務。
- 同一章節可管理多張候選圖，但只能明確指定一張主要成品。

### Phase 6：規模化與維運

目標：支援長篇小說數百章與大量角色資產。

交付物：

- SQLite 或等價索引層，圖片仍保留為普通檔案。
- 任務、角色、章節與狀態搜尋。
- 資料備份、遷移與 Schema 版本升級。
- 效能監控、批次失敗恢復與測試資料生成。
- 可重用子流程／模板，例如「單角色對話場景」與「雙角色戰鬥場景」。

完成條件：

- 數百章與數千候選圖下仍可搜尋、開啟與恢復工作流。
- 工作流和資料版本升級不破壞既有任務。
- 常用子流程可重用，但每個實例仍保留自己的參數與歷史。

## 12. 優先順序

### P0：先做，否則後續會重工

1. JSON Schema 與目錄契約。
2. 角色 Reference Set 與資產版本。
3. 真實畫布資料模型。
4. 桌面生圖任務狀態機。

### P1：形成第一個可用閉環

1. React Flow 畫布。
2. 批次匯出與圖片收件匣。
3. Level 0／1 驗收。
4. 人工核准與重試。

### P2：提高角色一致性與規模

1. Level 2／3 驗收。
2. 多角色與引擎能力適配。
3. 子流程模板與大規模索引。

## 13. 建議的第一個垂直切片

不要先完成所有節點再整合。第一個切片只處理秦無漏與三個場景：

1. 建立 `qin_woulou-core-v1` Reference Set。
2. 建立第 004、025、050 章三個 Scene Spec。
3. 在真實畫布連接角色、場景、Gemini Desktop Gate 與 Quality Gate。
4. 匯出一個三任務批次包。
5. 人工以桌面程式生成並匯回候選圖。
6. 執行 Level 0／1 驗收與簡化版角色相似度 PoC。
7. 在介面核准一張、退回一張並建立一次重試。
8. 儲存並重新開啟工作流，確認所有狀態與版本一致。

這個切片完成後，再擴張到更多角色與批量章節，能最早暴露資料模型、桌面交接與驗收流程的真正問題。

## 14. 待討論決策

以下決策在 Phase 0 結束前確認：

1. 前端是否採 Vite + React + TypeScript + React Flow。
2. 第一個桌面交接優先支援 Codex、Gemini，或兩者同時。
3. 角色基準圖是否允許 AI 自動裁切後直接使用，或必須逐張人工核准。
4. 第一版資料只用 JSON 檔，或一開始即加入 SQLite 索引。
5. 自動 QA 的錯誤偏好：寧可多攔截，或寧可少誤殺。
6. 核准資產是否直接提供給 Web Reader／遊戲引用。
7. 現有 Dashboard 是逐步遷移，還是保留為 Demo、另建正式 Studio。

## 15. 整體完成定義

當下列條件全部成立，可宣告 Visual Harness 1.0：

- 角色參考圖已資產化、版本化且可跨任務重用。
- 畫布是可編輯、可保存、可驗證的真實工作流圖。
- 可批量匯出桌面生圖任務並可靠匯回結果。
- 品質分數來自實際圖片，沒有固定假資料。
- 人工核准、退回、重試與成品追溯形成完整閉環。
- 任一成品可重現其角色版本、Prompt、引擎、候選圖與 QA 報告。
